# Story 3.9: Forward-Pick Replenishment (FR-W-08)

Status: review

## Story

As a warehouse manager,
I want forward-pick zones replenished automatically from reserve storage when min/max levels are breached or when open pick demand signals a shortfall,
so that high-velocity picking zones stay stocked without manual intervention.

## Acceptance Criteria

1. Given the forward-pick quantity for `SKU-RM0042` in zone `FP-ZONE-A` drops below its configured minimum (FR-W-08), when the replenishment trigger runs, then a replenishment task is created to move the quantity that tops the zone up to its configured maximum from reserve storage to `FP-ZONE-A`, and the task appears in the task board for assignment.
2. Given open pick demand for `SKU-RM0042` from the Story 2.9 sales-order projection exceeds the current forward-pick balance in `FP-ZONE-A`, even though the configured minimum has not yet been breached, when the replenishment trigger runs, then a demand-signal replenishment task is created for the shortfall quantity ahead of the min/max cycle (FR-W-08 demand signals).
3. Given a replenishment task completes, when the operator confirms the transfer, then the forward-pick balance updates immediately; the reserve balance decreases by the same quantity; both movements are traceable through the same `correlation_id` stored on the task and stamped on both domain events.

## Dev Notes

### Architecture Patterns and Constraints

- **Single write seam.** All domain state mutation goes through `persistEvent(envelope, auditCtx?, externalClient?)` in `src/events/store.ts`. Pre-transaction shape-assert functions run first, in fixed registration order, ending at `assertErpReadOnly(envelope)`; in-transaction `apply*Projection` functions run afterward, in the same fixed order, immediately before the `domain_events` insert. Story 3.9's asserts/applies splice in immediately after Story 3.8's `pick_task.assigned` blocks (Task 5.3). Never reorder or remove an existing assert or apply call — the Story 1.9 spine gate enforces this ordering as a hard invariant.
- **Event naming and stream tagging.** `replenishment_task.created`/`replenishment_task.completed` register on the existing `'warehouse'` stream with `requiresBusinessStream: false`, following the identical rationale already established for `pick_task.*`, `putaway_task.assigned`, and `dispatch.*`: the events are task-management/internal-relocation actions, and the `'warehouse'` stream sits outside `VALUATION_STREAM_TYPES = new Set(['inventory'])` in `src/compliance/inventory-valuation.ts`, so moving already-owned stock between two locations at the same cost basis never triggers a valuation event — exactly as it does not for `pick_task.completed`'s allocated-to-picked move or `dispatch.dispatched`'s on_hand decrement, both of which mutate `stock_balance` through direct calls, not through the `'inventory'`-stream-gated `applyStockBalanceProjection`.
- **Reuse `applyStockIssue`/`applyStockReceipt` directly, not `applyStockBalanceProjection`.** `src/compliance/stock-balance.ts`'s `applyStockBalanceProjection` only fires for `'inventory'`-stream `stock.received`/`stock.allocated`/`stock.issued` events (see `STOCK_BALANCE_STREAM_TYPES = new Set(['inventory'])`). The actual balance-mutating helpers it calls — `applyStockReceipt`, `applyStockAllocation`, `applyStockIssue`, `applyStockDeallocation` — live in `src/read/projections/stock_balance.ts` as plain, reusable functions. `src/compliance/transfer-request.ts` already calls them directly for its own ship/receive movements, outside the `'inventory'`-stream gate. Story 3.9's `applyReplenishmentTaskCompletedProjection` should do the same: call `applyStockIssue` at the reserve location and `applyStockReceipt` at the forward-pick bin directly, inside its own apply function — never route through `applyStockBalanceProjection`, which would silently no-op for a `'warehouse'`-stream event.
- **Zone-descendant walk is new; zone-ancestor walk already exists.** `src/read/projections/putaway_task.ts`'s `ZONE_ANCESTOR_CTE` and `src/warehouse/pick-task-generator.ts`'s equivalent both walk a *bin upward* to its owning zone. Story 3.9 is the first story to need the *opposite* direction — a *zone downward* to its bins, to sum `stock_balance.on_hand` across everything physically inside `FP-ZONE-A`. Task 4.1 specifies this new recursive CTE; do not attempt to adapt the existing ancestor CTE by reversing a join condition without re-deriving it, since the base case and recursive step both differ (ancestor starts at a bin and climbs `parent_location_id`; descendant starts at a zone and matches children *whose* `parent_location_id` equals the current frontier).
- **Reuse the depth-cap convention.** Both existing directional walks cap recursion at depth 10 to make a cyclic `parent_location_id` chain (which the register should never contain, but which would otherwise hang the query) terminate instead of infinite-looping. Task 4.1's new descendant walk must use the same cap.
- **`forward_pick_config` and `task_sla_config` are structurally the twin projections in this story** — both are supervisor-configured thresholds keyed by a grain that includes a zone, both use `site_id` in the grain for the exact reason Story 3.8's review added it to `task_sla_config` (a null-site row would let one site's supervisor silently change behavior everywhere). Do not re-derive this reasoning from scratch; it already failed once in Story 3.8 and was fixed there.
- **`replenishment_task` and `replenishment_recommendation` are siblings, not the same table.** `replenishment_recommendation` (Story 2.7/2.8) is a SKU-*location* reorder/VMI signal that Epic 4 will eventually turn into a purchase requisition — it has no zone concept and is never itself a task an operator executes. `replenishment_task` (this story) is a SKU-*zone* internal-movement task that appears on the Story 3.8 task board and is executed by a warehouse operator moving physical stock. The two tables' near-identical `signal_type`/partial-unique-open-index shape is a deliberate pattern reuse, not a sign they should be merged.
- **RBAC and SOD.** Auth is SSO-gated; every request is authenticated. `requireRole` gates a route by role list and resolves the module; `permittedLocationsForModuleScope` enforces site scoping. The established warehouse role vocabulary from Stories 3.5 through 3.8 is `warehouse_manager`/`inventory_controller` (supervisors), `store_assistant`/`warehouse_operator`/`dispatch_clerk` (frontline), and `unloading_supervisor` (receiving/putaway read+release). Story 3.9's read/confirm role list must explicitly enumerate every write-capable role alongside the frontline roles — the exact RBAC read-role regression Story 3.7 introduced and Story 3.8's `DISPATCH_READ_ROLES`/`WAREHOUSE_TASK_READ_ROLES` constants were built to prevent; never assume write-role membership implies read-role membership.
- **Error envelope.** `{ error_code, message, details, trace_id }`. New stable codes this story introduces: `FORWARD_PICK_ZONE_INVALID`, `REPLENISHMENT_TASK_NOT_READY`, `REPLENISHMENT_DESTINATION_OUTSIDE_ZONE`. Register these in the architecture's stable-error list if the project maintains one outside the code (Story 2.5's deferred-work notes that its own new codes were *not* added to a planning-artifact list — do not repeat that omission if such a list exists and is kept current).

### Previous Story Intelligence (Story 3.8)

Concrete, actionable learnings from Story 3.8's implementation and review, directly applicable here:

- **The task-board extension point exists because Story 3.8 built it for this exact story.** `src/warehouse/task-metrics.ts`'s `TASK_SOURCES` array is explicitly documented as "kept as data rather than a hard-coded UNION so Story 3.9's replenishment tasks (and anything after it) can join the board by appending one entry, with no change to the query builder or the response contract." Use it as designed (Task 3.3) — do not rebuild a parallel board or duplicate the SLA-threshold/age-computation logic.
- **`site_id` belongs in a config grain, not just as decoration.** Story 3.8's review found `task_sla_config` originally had no `site_id` in its grain, letting a single-site supervisor silently change SLA behavior for every site in the deployment. `forward_pick_config` (Task 2.1) is built with `site_id` in the grain from the start, avoiding a second occurrence of the identical defect class.
- **A direct-to-read-model write with no domain event is a known, deliberately-accepted inconsistency elsewhere (`assignPickTask`), but Story 3.8 fixed the same pattern for putaway assignment by making it an event instead (`putaway_task.assigned`).** Story 3.9 follows the *event* pattern (Task 5) for both task creation and completion, not a direct write, so replenishment tasks replay, audit, and pass through the compliance seam exactly like every other Story 3.5-3.8 warehouse write — consistent with the more recent, more correct precedent, not the older inconsistency.
- **RBAC read-role regression is the single most repeated defect class across Stories 3.6, 3.7, and 3.8's reviews.** Each time, a round of fixing write-role gating accidentally narrowed or forgot read-role gating for the same roles. Define `REPLENISHMENT_READ_ROLES` (Task 6.1) explicitly enumerating every write-capable role alongside frontline roles from the start, rather than fixing this after a review pass finds it.
- **SOD/role checks must live in the compliance seam, not only the HTTP handler.** Story 3.8 Task 7.3 put the `task_sla_config.updated` SOD check inside `src/compliance/warehouse-task.ts` specifically so a direct `POST /api/v1/events` call could not bypass a handler-only check. Task 2.2/5.2 apply the identical discipline to the `FORWARD_PICK_ZONE_INVALID` and destination-zone checks.
- **Server-set actor identity fields must come from the envelope's actual actor metadata, never a placeholder string.** A Story 3.7 round-1 bug used the literal `'unknown'` for an actor field, violating a `NOT NULL` constraint. Source `completed_by`/`assigned_by` from `authContext`/`envelope.metadata.actor.user_id`, never a placeholder (Task 5.2, 6.4, 6.5).
- **Grants must be copy-checked literally against the DDL task spec.** A Story 3.8 round-1 table grant included `DELETE` when the spec said INSERT/SELECT/UPDATE only. Copy Task 2.1/3.1's exact grant lists verbatim.
- **Mirror the prior story's integration-test file structure, but pick the one that actually executes.** Story 3.8 explicitly mirrored Story 3.6's test file rather than Story 3.7's, because Story 3.7's harness never ran at all (a broken `before` hook posting to an unregistered SCIM route). This story mirrors Story 3.8's file for the same reason — it is the most recently confirmed-executing warehouse integration suite.
- **Verify a fix (or a new feature) by asserting on the actual response body, not just a 200 status.** Confirm the confirm/assign/config endpoints actually return the fields the ACs imply (quantity, correlation_id, zone_id, status) in tests, not only that they return success.

### Project Structure Notes

### Review Findings

- [x] [Review][Decision] POST /assign bypasses persistEvent — `src/api/v1/replenishment.ts:269-316` calls `assignReplenishmentTask` directly with no domain event, no audit trail through the seam, and no replay safety. Spec Task 6.5 says "mirrors PUT /api/v1/putaway-tasks/:id/assign (Story 3.8)" which uses persistEvent via `putaway_task.assigned`. No `replenishment_task.assigned` event type is defined. **Resolved:** Add `replenishment_task.assigned` event type for full event-sourced parity with Story 3.8 (requires schema, compliance, store.ts changes).
- [x] [Review][Decision] Application-level duplicate check violates spec constraint — `src/warehouse/replenishment-job.ts:115-124` performs a SELECT for existing ready tasks before persistEvent. Spec Task 5.4 explicitly says "do not add a separate application-level duplicate check that could drift out of sync with the index." The code comment explains it's an optimization to avoid constraint errors on sequential re-runs; the partial unique index is the concurrency backstop. **Resolved:** Keep the defensive read; update spec Task 5.4 to reflect the actual design (read optimization + index backstop).
- [ ] [Review][Patch] Add replenishment_task.assigned event [src/events/schema.ts] — Decision 1 resolved: add `ReplenishmentTaskAssignedPayload/Envelope`, register `replenishment_task.assigned` in `SUPPORTED_EVENT_TYPES`, add assert/apply in `src/compliance/replenishment.ts`, splice into `src/events/store.ts`, and update `src/api/v1/replenishment.ts:269-316` to call `persistEvent` instead of `assignReplenishmentTask` directly.
- [ ] [Review][Patch] Update spec Task 5.4 to document defensive read [src/warehouse/replenishment-job.ts:115-124] — Decision 2 resolved: update spec Task 5.4 to document the application-level read as an optimization to avoid constraint errors on sequential re-runs, with the partial unique index as the concurrency backstop.
- [ ] [Review][Patch] No reserve bin available creates uncompletable task [src/warehouse/replenishment-job.ts:152] — when no reserve bin has sufficient available stock, `fromLocationId` is null, the task persists with null source, confirm throws 409 at `src/compliance/replenishment.ts:290-294`, and the partial unique index blocks re-runs for the same (sku, zone, signal_type). Fix: skip task creation if no source bin found, return skip reason.
- [ ] [Review][Patch] Destination equals zone_id allows zone-level stock [src/compliance/replenishment.ts:314] — the descendant check `if (destination.location_id !== task.zone_id && descendantCheck.rows.length === 0)` allows the destination to be the zone itself (not a bin). Stock at zone level corrupts balance queries that assume bin-level granularity. Fix: add level check requiring destination to be a bin.
- [ ] [Review][Patch] No FK on replenishment_task.zone_id [read/projections/replenishment_task.sql:22] — zone_id has no REFERENCES clause to location_register(location_id). forward_pick_config has the FK. The runtime check in assertForwardPickZone is the only guard; a direct SQL insert or event replay could create orphan rows. Fix: add FK.
- [ ] [Review][Patch] from_location_id not validated as reserve zone [src/compliance/replenishment.ts:215-222] — only checks existence and active status, not that the location descends from a reserve zone at the task's site. A direct event POST could set from_location_id to any active location (e.g., another forward-pick zone or a staging bin). Fix: add reserve zone validation in the compliance seam.
- [ ] [Review][Patch] Assignee has no site access check [src/api/v1/replenishment.ts:269-316] — no verification that assigned_to can see the task's site. Task is assigned to an operator who cannot see or act on it through the site-scoped task board, creating orphaned work. Fix: add site access check for assignee.
- [ ] [Review][Patch] No test for to_location_code confirmation path — assertReplenishmentTaskCompletedShape validates the either/or to_location_id/to_location_code contract, and applyReplenishmentTaskCompletedProjection resolves via getLocationByCode when a code is provided. No integration or unit test exercises this path. Fix: add integration test.
- [ ] [Review][Patch] from_location_id not validated as UUID in shape assert [src/compliance/replenishment.ts:157-184] — assertReplenishmentTaskCreatedShape doesn't check from_location_id format. A non-UUID string causes an unhandled Postgres error (invalid input syntax for type uuid) instead of a clean 400 from the shape assert. Fix: add UUID validation.
- [x] [Review][Defer] Concurrent checks select same reserve bin [src/warehouse/replenishment-job.ts:129-151] — no lock on source bin selection. Two concurrent checks for different (sku, zone) pairs at the same site could select the same reserve bin. If the bin's available covers each individually but not both, the second completion drives stock_balance.available negative or fails with INSUFFICIENT_STOCK, leaving an orphaned task. deferred, pre-existing — Phase-1 limitation; FEFO/velocity ranking and bin locking are future enhancements.
