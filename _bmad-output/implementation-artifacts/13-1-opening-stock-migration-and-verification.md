# Story 13.1: Opening Stock Migration and Verification

Status: done

## Story

As a migration lead,
I want physically-verified opening stock imported by location, lot, and serial into staging with a variance report against ERP and legacy records,
so that we start with a proven, reconciled opening balance.

## Sequencing

Story 13.1 opens Epic 13 and is the first of three pilot-gate stories: 13.1 opening stock, then 13.2 active documents, then 13.3 the go-live sign-off gate. It is the pilot's last code story before deployment work begins. Everything the pilot slice needs (Epics 1, 2, 3, 5, 7, 8, 9 and Story 11.2) is done and committed; Story 11.5 is also committed and is outside the pilot slice. Story 13.3 consumes two things this story builds: the per-site `migration_stage` row and the opening-stock variance query. Story 13.2 reuses the `migration_stage` table for its document domains. Build both so they are domain-parameterised from day one.

## Acceptance Criteria

1. **Given** physically-verified opening stock (FR-DM-01)
   **When** it is imported into the staging environment
   **Then** it is loaded by location, lot, and serial with each row attributed to its physical-verification source

2. **Given** migrated opening balances (FR-DM-01)
   **When** the variance report is run
   **Then** migrated balances are compared to ERP and legacy records and every variance is listed

3. **Given** an unexplained variance (FR-DM-01, SM-48)
   **When** promotion from the staging load to the dry-run stage is attempted
   **Then** promotion is blocked with `error_code: "VARIANCE_UNRESOLVED"` until the variance is explained (a recorded variance-explanation entry naming cause and approver) or resolved (a corrected import row)

4. **Given** an import file containing malformed rows or rows referencing unknown item or location codes (FR-DM-01)
   **When** the import is run
   **Then** each failing row is rejected with a row-level `error_code: "MALFORMED_ROW"` or `error_code: "UNKNOWN_REFERENCE"`, valid rows still load, and a rejected-row report lists every rejection with its source file and line

5. **Given** an import row whose lot or serial number duplicates one already loaded (FR-DM-01)
   **When** the import is run
   **Then** the row is rejected with `error_code: "DUPLICATE_LOT_SERIAL"` and appears on the rejected-row report

6. **Given** an import run that failed partway (FR-DM-01)
   **When** the corrected file is re-submitted
   **Then** the import resumes without duplicating previously accepted rows - already-loaded rows are suppressed idempotently as `DUPLICATE_EVENT`, and only new or corrected rows are applied

## Dev Notes

### Why this story is pilot scope and what it is not

The pilot site goes live on migrated balances; SM-48 is "zero unexplained opening-balance variance at cutover with full sign-off" and the PRD's own warning is that "an error here repeats its damage on every transaction after cutover" (`_bmad-output/planning-artifacts/prds/prd-Inventory Management System_2-2026-07-10/archive/prd.md:443,507`). This story owns the opening-stock half of that guarantee: the staging load, the variance report, the explanation record, and the staging-to-dry-run promotion. It does not own department-head or finance sign-off (13.3), does not migrate BOMs, POs, challans or custody registers (13.2), does not migrate the asset register (Epic 17), open sales orders (Story 2.9 projections, verified there) or open gate passes (Epic 20), and does not build an IRP or ERP extract: the platform ingests a balance snapshot that the ERP or legacy side extracts, exactly as Story 2.9 ingests orders.

### Binding decisions

1. **The epic's data source claim is not backed by code, so this story builds the snapshot projection.** The epic says ERP and legacy balances "come from the same read-only ERP staging views that feed Story 2.9's projections". There is no ERP stock-balance, legacy-balance, table, view or `erp_sync_state` key anywhere in the repository; `src/adapters/erp/sync.ts` ingests purchase orders, sales orders and BOM records only. Task 4 adds `erp_stock_balance` as a third inbound record type on the same adapter, same per-record SAVEPOINT isolation, same exception queue, same heartbeat. It is a direct-upsert adapter-owned read model, not event-sourced, by the precedent `read/projections/erp_purchase_order.sql` sets and states in its header.
2. **The staging load is its own projection, not `stock_balance`.** Nothing in the codebase has a staging, dry-run, cutover or site-activation concept; `location_register.zone_type = 'staging'` is a physical zone and must not be overloaded. Imported rows live in `migration_opening_stock_row` until promotion. The live ledger (`stock_balance`, `lot_master`, `serial_master`, `inventory_valuation`, `lot_trace`) is written exactly once, by the `migration.stage.promoted` applier, atomically. Promotion is the boundary between "data under review" and "data the system runs on", which is what dry-run means.
3. **Epic 13 has no assigned module in the architecture capability map, so the RBAC module is `migration`.** RBAC modules are free strings matched against SCIM assignments (`src/middleware/rbac.ts:33-59`); no table needs a row. Write routes take `functionScope: 'write'`, read routes `'read'`, and site scope comes from the same assignment that grants the function (the events-door docblock rule that Story 11.5 found the REST routes violating).
4. **One event per accepted row, one stream per file.** `lot_trace` has a unique index on `event_id`, so a single bulk event could carry the genealogy of at most one lot. Per-row `migration.opening_stock.loaded` events give each lot its own origin event, give AC 6 its `DUPLICATE_EVENT` semantics for free through `persistEvent`'s duplicate path with `strictDuplicate: true`, and keep every row auditable. Row events use `stream_id = load_id` so two files for the same site never contend on one stream's optimistic version; site-level events (`import.completed`, `variance.*`, `stage.promoted`) use `stream_id = site_id`.
5. **AC 5 and AC 6 are reconciled by import mode.** AC 5 rejects a lot or serial "already loaded"; AC 6 applies "corrected rows". The row idempotency key is the SHA-256 of the row's content, so an identical resubmission is `DUPLICATE_EVENT` (suppressed, AC 6) and a differing row on a live grain is `DUPLICATE_LOT_SERIAL` in `initial` mode (AC 5) or a supersession in `correction` mode (AC 6). The mode is explicit per file so a typo in a fresh file cannot silently overwrite a verified row.
6. **Valuation follows the class sets, not class names.** `owned` rows must carry `unit_cost` (else `MALFORMED_ROW`) and post cost layers by the item's `valuation_method`, because Story 2.4 requires opening-stock cost layers and the 2026-09-05 noise-floor triage proved that received stock with no cost exists but can never be issued. Rows in `CUSTOMER_OWNED_STOCK_CLASSES` (`job_work`, `offcut`) post quantity only, at zero value, per the Story 9.10 ruling at `src/compliance/cycle-count.ts:1404`. Rows in `SUPPLIER_OWNED_STOCK_CLASSES` (`consignment`, `vmi`) also post at zero value (Open Question 2). `inventory-valuation.ts` already gates to `'owned'`, so this is consistent by construction; the story imports the sets and never restates the names (the `offcut` lesson: a class added to the vocabulary left three consumers unwalked).
7. **Variances are computed, not stored; explanations are stored and keyed.** A materialised variance table would need a "variance run" event and would go stale the moment a corrected row lands, which AC 3 explicitly counts as a resolution. `computeOpeningStockVariances` is one SQL statement used by the report and by the gate, in the handler and in the applier. Explanations bind to a deterministic `variance_key` and record the delta they explain; a delta that later changes makes the explanation `stale` and the gate blocks again. SM-48 says unexplained, not once-explained.
8. **The approver is resolved server-side and frozen, and approval is a second event by that actor.** `resolveApprover('migration.variance_explanation', abs(value))` decides who; the explainer cannot approve; the approver must be the authenticated caller. This is the Story 2.6 count-adjustment mechanic and the Story 9.9 forgery fix applied to a new transaction type. A poster-supplied `approver_actor_id` is the exact gap Story 9.9 closed and it is not reopened here.
9. **The physical-verification source reference is external text, not a `physical_verification_id`.** Pre-go-live counts happen on paper or in the legacy system; `physical_verification` rows are Story 2.6's in-system evidence and do not exist yet. `pv_ref_ext` and `pv_line_ref_ext` satisfy AC 1's attribution; the `_ext` suffix is the architecture's convention for external identifiers (`ARCHITECTURE-SPINE.md:172-187`).
10. **The `migration` stream is barred on both event doors.** The only producers are this story's REST routes, which parse, validate and site-scope. A direct or edge-sync `migration.*` envelope is refused by the same mechanism that refuses the `maintenance` stream, before any assert consumes an idempotency key. Payloads still carry `site_id` so the central `assertPayloadSiteWriteAccess` gate would bind if the bar were ever lifted. None of the codes are added to either `PERMANENT_ERROR_CODES` set.
11. **The template is a byte-exact header contract.** Column order and names are the version; a mismatch refuses the whole file. Looser matching is how a `unit_cost` column ends up read as `quantity`.
12. **`location_current` is not seeded for opening lots.** The Story 3.6 review moved substituted-lot bin resolution from `location_current` to the authoritative `stock_balance` row precisely because never-scanned lots have no `location_current`. Opening lots are never-scanned lots. If a pilot read path is found to need it, that is an Open Question 8 finding for the dev record, not a silent extra write.

## Open Questions

None of these block development; each has a stated default the tasks follow.

1. **Post at promotion or at go-live.** Default: the `migration.stage.promoted` applier posts the live ledger (Binding Decision 2), so dry-run runs on real balances and Story 13.3's go-live only activates transactional posting. Alternative: keep the ledger empty until 13.3's unblock event and post there; that leaves dry-run with nothing to run on.
2. **Supplier-owned classes.** Default: `consignment` and `vmi` post at zero value, quantity only, because they are not the company's inventory under Ind AS 2 and `inventory-valuation.ts` already ignores them. If finance wants a memorandum value, add a `declared_unit_cost` report column; the column already exists on the row.
3. **CSV transport.** Default: the file travels as a UTF-8 string in the JSON body (`csv`), capped at 10,000 data rows under the existing 10 MB body cap (413 `PAYLOAD_TOO_LARGE`, which `src/middleware/body.ts` already mints), because the body parser is JSON-only and the house style adds no dependency. Multipart upload is a Phase 2 nicety.
4. **DOA bands for `migration.variance_explanation` in production.** Default: seed a single band from `value_min = 0` to `finance_controller` for the pilot; the CFO band above it is a registry decision for finance before dry-run, not code.
5. **Reverse promotion.** Default: unsupported. A site promoted in error is a database restore of the staging environment, which the architecture already defines as disposable single-node Compose (`ARCHITECTURE-SPINE.md:307`). Say so in `docs/migration/opening-stock-template-v1.md`.
6. **Row event volume.** Default: sequential per-row `persistEvent`, expected under two minutes for 10,000 rows on the test database; measure and record. If the measured figure is over five minutes, batch rows into one transaction per 500 while keeping one event per row, and record the change in the Change Log.
7. **Legacy extract ownership.** Default: the legacy side produces the same `SourceStockBalance` shape with `source_system = 'LEGACY'` and pushes it through the existing sync-trigger route under the `svc_erp_adapter` identity. If a separate service identity is wanted, it is a SCIM provisioning matter, not a code change.
8. **`location_current` for opening lots.** Default: not written (Binding Decision 12). If Task 9.7's issue-through test or any Story 3.x path fails on a never-scanned lot, record the path and stop; do not add the write without a ruling.
