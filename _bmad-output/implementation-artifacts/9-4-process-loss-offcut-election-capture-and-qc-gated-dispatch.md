# Story 9.4: Process Loss, Offcut Election Capture, and QC-Gated Dispatch

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a job-work supervisor,
I want process-loss norms with over-norm approval, contractual offcut election captured at confirmation, output through the FG QC gate before dispatch, and partial dispatch support,
so that loss is controlled, offcut terms are fixed per contract, and only quality-released output ships.

## Acceptance Criteria

1. **Over-norm loss requires approval (FR-JW-08).** Given a job with a configured process-loss norm, when a supervisor declares process loss on an order and the declared loss (as a percent of the order's cumulative customer material consumed to date) exceeds the configured norm, then the declaration is blocked with `error_code: "APPROVAL_REQUIRED"` until a supervisor holding the DOA-resolved approval authority approves it (Story 6.1/6.3 release-override chain: acting user must be the resolved approver). Loss at or below the norm posts without approval.
2. **Loss posts to the custody ledger (FR-JW-05, FR-JW-08).** Given an approved (or within-norm) loss declaration, when it is recorded, then a `loss` row (negative delta, `ownership = 'customer'`) is written to the Story 9.3 `custody_ledger_entry` for the declared sku, decrementing the customer's custody balance by the declared quantity, attributed to the declaring user.
3. **Offcut election captured at confirmation, mandatory when contractual (FR-JW-09/10).** Given an order flagged as having a contractual offcut arrangement, when the order is confirmed without an `offcut_election` (`return`, `retain_and_buy`, or `retain_free`), then confirmation is blocked with `error_code: "INVALID_STATE_TRANSITION"`. Given the flag is set and an election is supplied, then confirmation succeeds and the election is captured on the order (already-existing optional column; this story makes it mandatory under the flag). Given the order has no contractual offcut arrangement, election stays optional as today. Execution of the elected disposition is Story 9.6.
4. **Dispatch blocked until FG QC gate release (FR-JW-11).** Given finished job-work output, when dispatch is attempted before every named output lot has passed the FG QC gate (Epic 8 — no `qc_hold` and no un-released conditional release), then dispatch is blocked with `error_code: "LOT_ON_HOLD"` naming the blocking lot(s).
5. **Partial dispatch decrements custody and generates documents (FR-JW-11).** Given a QC-released order, when the customer accepts a partial shipment, then the dispatch reduces the order's open-to-dispatch quantity for that output lot, writes a `dispatch` row (negative delta, `ownership = 'customer'`) to the custody ledger for the consumed customer material apportioned to the dispatched output quantity, and generates dispatch documents (BOL, packing slip, commercial invoice, label) via the Story 3.7 document renderers, with only QC-released quantities dispatchable and each dispatch attributed to the dispatching user.

## Dev Notes

### Binding scope decisions (read before coding)

1. **Job-work output has no existing production/completion concept to extend.** Epic 9 never built a "job-work processing" step before this story; Stories 9.1-9.3 only cover order lifecycle, receipt, and consumption. Story 8.1's `receiveQcCompletion` contract already reserves `source_completion_type: 'job_work_order'` and a `job_work_order` union member on `source_order_type` — this story is the FIRST caller of that reserved contract. Read `src/quality/completion.ts:11-54` fully before writing `jobwork-output.ts`; do not re-derive what that function already owns (lot creation, WIP, valuation, QC hold — none of it belongs in this story's code).
2. **The kit BOM's parent item is the job-work output item.** No output-item field exists on `service_order`; resolve it from `getBomById(order.kit_bom_id).item_id` at output-recording time (current revision, no pin, consistent with 9.3 decision 5's kit-BOM handling).
3. **Loss is DECLARED, not computed as a receipt/output difference.** This mirrors the existing `production_scrap_declaration` precedent (declared quantity + reason code, not a derived diff) rather than inventing a yield-reconciliation formula the spec does not define. The norm check compares the declared quantity against cumulative customer consumption for that sku, not against output quantity (the codebase has no per-line yield/BOM-consumption-ratio field to compute an alternative basis against).
4. **The Story 3.6/3.7 pick/pack/dispatch state machine (`dispatch_order_status`) is sales-order-bound and NOT reused for job-work dispatch.** `getDispatchOrderStatus` inner-joins `erp_sales_order`; a job-work order has no sales-order line. Only the QC-gate check (`qcGatedLotIds`) and the document renderers/`dispatch_document` table (schema-agnostic UUID key, no FK) are reused. A new minimal `job_work_output` projection tracks per-lot dispatched quantity, since nothing in the codebase does this for a non-sales-order-keyed demand line today. Disclose this as a deviation from a literal "reuse Story 3.7 flows" reading — the epics dev-note only requires dispatch DOCUMENTS through Story 3.7's flows, not its pick/pack state machine.
5. **The custody-ledger `dispatch` apportionment across multiple customer-supplied kit skus is a judgment call**, not specified by the epic. Task 4.4 states the simplest defensible pro-rata rule and requires disclosing it in the Debug Log. If the PO has a different intended allocation (e.g., FIFO by receipt, or per-line fixed ratios from the kit BOM), that is a follow-up change, not a blocker for this story — the custody ledger's ultimate correctness is that its balance reaches zero at closure (Story 9.5 `CUSTODY_NOT_ZERO`), which any consistent apportionment rule satisfies.
6. **`has_contractual_offcut` is a new boolean, not inferred from anything existing.** No field distinguishes "this order has a contractual offcut arrangement" from "it does not" prior to this story. Adding a plain boolean (default false, so all 9.1/9.2/9.3 fixtures are unaffected) is simpler and more auditable than inferring intent from `price_basis` or the kit BOM.
7. **Over-norm loss approval reuses the Story 6.1/6.3 DOA chain verbatim** (`resolveApprover`, `APPROVAL_UNRESOLVED`, forged-`approved_by` rejection, acting-user-is-approver rejection) — this is the third use of this exact pattern (6.1 release override, 6.3 over-completion/short-close); do not invent a variant. The new `jobwork.over_norm_loss` DOA transaction type must be seeded in the DOA registry by ops/config before the approval path is reachable — no code seeds DOA entries, consistent with every other `resolveApprover` caller.
8. **`custody.loss_recorded` rides the EXISTING `custody` stream**, not a new stream — Story 9.3 already registered the stream type and forward-declared the `loss` category's sign rule in the CHECK constraint specifically for this story to use without a migration.

### Critical defect classes to not reintroduce (from 9.1-9.3 review history)

- **Hold-bypass class** (8.3-8.8, 9.3): every gate (norm check, QC-gate check, contractual-offcut check, lot-under-order check) re-derived under the order advisory lock, never trusted from a route pre-check. The generic `/api/v1/events` route must hit the same seam gates as the dedicated routes.

- **Closed-shape payloads and `rejectUnacceptedFields`** symmetric on every new mutating route (9.1/9.3 convention).
