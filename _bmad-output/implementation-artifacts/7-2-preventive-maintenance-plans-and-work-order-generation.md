## Story

As a maintenance planner,
I want calendar-based and meter-based PM plans that auto-generate work orders with grace-window tracking, fed by a generic meter-reading ingestion API whose Phase-1 primary source is manually entered readings,
So that preventive maintenance happens on schedule without manual creation.

## Acceptance Criteria

1. **Given** an asset from Story 7.1, **When** a calendar-based or meter-based PM plan is defined (FR-M-02), **Then** the plan auto-generates work orders as due, tracking each against its grace window.
2. **Given** a generated PM work order that passes its grace window uncompleted (FR-M-02), **When** the grace window expires, **Then** the work order transitions to an overdue state and an escalation alert is raised to the maintenance planner.
3. **Given** a meter-based PM plan (FR-M-03), **When** a technician or operator submits a manual meter reading against the asset, **Then** the reading is accepted through the meter-reading ingestion API, the asset's usage meter advances, and PM due calculations update accordingly.
4. **Given** the meter-reading ingestion API (FR-M-03), **When** a reading arrives from any registered source (manual entry in Phase 1; hub bookings and station equipment when their feeds come online), **Then** the reading is applied identically regardless of source, and each reading records its source and capture method.
5. **Given** a meter that has reported no readings for a configured interval, **When** the monthly reconciliation runs, **Then** a silent-meter alert is raised and the meter is reconciled.

## Dev Notes

### Binding Scope Decisions

- This story builds directly on Story 7.1 (done, commit ce42587). The `maintenance` stream, the `asset` projection, the `src/compliance/asset.ts` seam, and the `assets` REST surface all exist. REUSE them. Do not create a second asset concept, do not add a second duplicate-detection helper, do not re-establish the stream.
- Scheduling is POST-triggered, NOT cron. This codebase has no scheduler for business jobs: `runSafetyStockComputation`, `runReplenishmentCheck`, and `runObsolescenceScan` are all invoked by authenticated POST endpoints carrying an explicit `business_date`. The only `setInterval` in the process is the Story 1.11 notification dispatcher, deliberately started in `startServer()` and never in tests (`src/server.ts` lines 682-728). Follow the POST-with-`business_date` pattern: it is deterministic, testable, and the established convention. Do NOT add `node-cron`, a timer, or a new container.
- "Monthly reconciliation" (AC 5) therefore means "the reconciliation job, run monthly by the operator or an external scheduler", not an in-process monthly timer. The job is idempotent so a duplicate invocation is harmless.
- Anti-double-generation key (CONFIRMED): `uq_maintenance_work_order_cycle` on (plan_id, generated_for_cycle). Without it, two generation runs on the same day - or two concurrent runs - produce duplicate work orders for one due cycle, which is the single most damaging failure mode in this story. The seam pre-check under `FOR UPDATE` gives the stable `DUPLICATE_WORK_ORDER`; the partial unique index is the backstop; the 23505 mapper resolves the winner (the Story 7.1 review decision).
- Meter readings are monotonic non-decreasing (CONFIRMED): a reading below the stored `current_reading` is rejected with `METER_READING_REGRESSION` 409. Meter rollover and meter replacement are NOT handled in this story; they need a deliberate reset event and are out of scope. An EQUAL reading is accepted - it is a valid "no usage since last report" observation and it refreshes `last_reading_at`, which is exactly what the silent-meter check reads.
- Work-order completion IS in scope, minimally. AC 2 is untestable without a completed state (the grace sweep must not escalate a completed order), so this story delivers `maintenance.work_order_completed` and `POST /api/v1/maintenance/work-orders/:workOrderId/complete` carrying nothing but the actor. Closure codes, labour, downtime, and spare-parts consumption are Stories 7.3 and 7.8 - do NOT pre-build them.
- Work-order table is shared with Story 7.3 (breakdown work orders) by design: `origin` already admits `'breakdown'` and `plan_id` is nullable, guarded by `chk_maintenance_work_order_plan_link`. Story 7.2 only ever writes `'preventive'`. Do not build breakdown routes, priority-by-criticality ordering, or fault reporting here.
- Meters are an explicit registered entity (`asset_meter`), not a column on `asset`. AC 4 requires readings from multiple named sources against a stable target and AC 5 requires a per-meter configured silent interval; one asset can carry more than one meter (running hours and cycle count). Readings target `meter_id`.
- `asset_meter.alert_role` and `maintenance_plan.escalation_role` carry the notification target as DATA captured at registration time. This satisfies AC 2 ("escalation alert is raised to the maintenance planner") without a role-name literal in control flow, which `eslint-rules/no-hardcoded-role-in-workflow.js` forbids.
- No FOREIGN KEY constraints between projections. `asset.sql` declares none and the codebase's projections are event-rebuildable read models; referential integrity is enforced by seam existence checks (`ASSET_NOT_FOUND`, `METER_NOT_FOUND`, `PLAN_NOT_FOUND`) inside the transaction, matching the Story 7.1 pattern.
- No edge or offline path. Offline technician capture is Story 7.8; `src/sync/upload.ts`, `edge/src/sync/connector.ts`, and `edge/src/messages/en.json` are NOT modified. No hub-booking or station-equipment feed is built (the epics note defers both; the ingestion API simply accepts their `source` values today).
- There is NO user-facing screen in this story: central-plane REST API only. No UX contract document exists for this domain.
- No new dependencies, no PostgreSQL extensions, no web framework. The stack is Node 24 with `node:` builtins, `pg` 8.16, `jose`, `web-push`, TypeScript 5.8 ESM (`.js` extensions on relative imports), tested with `node:test` and `node:assert/strict`.

### Job Engine Contract

- `src/maintenance/pm-jobs.ts` is a new file in a new `src/maintenance/` directory. - Race and sequential duplicate paths must return the SAME error code with the same `existing_*` detail. Resolve the winning row in the 23505 branch (`resolveAssetDuplicateConflict` is the template).
