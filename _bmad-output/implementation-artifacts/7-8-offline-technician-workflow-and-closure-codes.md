# Story 7.8: Offline Technician Workflow and Closure Codes

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a maintenance technician,
I want my day-to-day workflows (fault reporting, work-order status updates, meter readings, spares issue confirmation, and work-order closure) to function fully offline with clean sync, conflict flagging, and three-part closure coding,
so that maintenance work continues uninterrupted in the plant and every closure builds the asset's failure history.

## Acceptance Criteria

1. **Given** a technician device operating offline (FR-M-17)
   **When** fault reports, work-order status updates, meter readings, spares issue confirmations, or work-order closures are captured
   **Then** each is stored locally with an `idempotency_key` and, on reconnection, replayed in sequence with duplicate suppression via `error_code: "DUPLICATE_EVENT"`

2. **Given** an offline-captured event that conflicts with a change accepted centrally while the device was offline (FR-M-17)
   **When** the replay is processed
   **Then** the conflicting event is rejected with `error_code: "STREAM_CONFLICT"`, flagged in a sync-conflict queue, and surfaced to the maintenance supervisor for resolution

3. **Given** a work order is submitted for closure (FR-M-18)
   **When** closure codes are applied
   **Then** three-part closure coding (fault, cause, and remedy) is recorded, and closure is rejected until all three codes are present

4. **Given** a work order is opened for an asset (FR-M-18)
   **When** the technician views the work order
   **Then** the last five closures for that asset (fault, cause, remedy) are presented at work-order open

**Epic note (binding):** Offline behavior covers the technician flows delivered in Stories 7.2-7.6 and follows the Epic 1 edge sync foundation (PowerSync, idempotency keys). Return-to-service sign-off (Story 7.6) remains a central-only operation.

| 2 | Conflict detection is per-stream optimistic concurrency through `event_version`. Meter readings OMIT `event_version` so the server assigns `MAX + 1`; they never raise `STREAM_CONFLICT` (additive observations), and the existing `METER_READING_REGRESSION` 409 is the semantic guard. ### Edge Capture and Version Contract (AC 1, 2)

- Every maintenance capture is one `edge_outbox` row built by `createOutboxEvent` with `stream_type: 'maintenance'`, `metadata.device_id`, `metadata.capture_method: 'MANUAL'`, a key prefixed `edge-<flow>-`, and `local_status: 'pending_sync'`. The connector is the only uploader; components never call the API for writes.
- Version stamping per Decision 2 is summarised in Table 4 and is the single most important rule in the edge half of this story: a wrong `event_version` either never conflicts (silent overwrite risk) or always conflicts (dead flow).

**Table 4: Version Stamping per Flow**

| Flow | `stream_id` | `event_version` on the device | Why |
| --- | --- | --- | --- |
| Fault report | new `fault_report_id` | 1 | Fresh stream; a version-1 collision is impossible |
| Work-order status update | `work_order_id` | `local_head_version + 1` (bumped) | Existing stream; central changes must conflict |
| Meter reading | `meter_id` | omitted (null) | Additive observation; server assigns MAX + 1; `METER_READING_REGRESSION` guards semantics |
| Spares issue confirmation | `reservation_id` | `local_head_version + 1` (bumped) | A central cancel or issue must conflict |
| Work-order closure | `work_order_id` | `local_head_version + 1` (bumped) | Same stream as status updates; sequence preserved |

- `local_head_version` lives on `cached_work_order` / `cached_spare_reservation`, seeded from the worklist `stream_version` and bumped by `nextStreamVersion` at capture time. A worklist refresh never lowers it while that stream has unsettled outbox rows.
- Parking (Decision 3) is decided from the outbox table at upload time (`hasUpstreamStreamConflict`), so it survives app restarts and PowerSync transaction boundaries. The device clock orders the chain; equal timestamps park.
- Server-side, a declared version is accepted ONLY when it equals `head + 1` (Decision 2). The store inserts any declared version (`src/events/store.ts:978`), so the handler is the gap guard; `STREAM_CONFLICT` therefore means "not the next version," not merely "that version is taken."
- Benign rebase (Decision 16) is the only automatic re-versioning in the platform: gap read, then one retry with a DECLARED `head + 1`. A collision on the retry is a real conflict.

### Sync-Conflict Queue Contract (AC 2)

- Raised by the server, never by the device: the device only ever sees the 409. The raise envelope's `metadata.actor` is the DEVICE actor (technician user, role, site), so `captured_by` and the notification `location_id` are derived from the same source as every other maintenance seam.
- Grain: one row per `conflicting_event_id`; a re-POST of the same conflicting event replays the raise (same `idempotency_key`) and returns the same `conflict_id`.
- Two reasons, one queue: `version_conflict` (AC 2) and `safety_fault_rejected` (a safety-flagged fault that met a permanent rejection on replay). The second exists so a safety fault can never disappear on one tablet; every other permanent rejection stays device-side.
- `head_version` is the stream's `MAX(event_version)` at raise time; `expected_version` is the device's declared version. Both are informational for the supervisor; nothing in the platform re-applies the payload.
- Resolution is DOA-gated in the seam (Decision 6). Seed `maintenance.sync_conflict_resolution` for `maintenance_supervisor` in tests; production seeds it through the same Story 1.4 API.

### Closure Code Contract (AC 3, 4)

- Format (shape assert, pre-transaction): trimmed, non-empty, at most 64 characters, no `\r\n,`, all-or-none.
- Presence (applier, under the work-order lock): mandatory for `origin = 'breakdown'`.
- Validity (applier): membership in the configured catalogue for each kind, case-sensitive, exact.
- Persistence: one `maintenance_work_order_closure` row per completed work order that carried codes; the codes are NOT copied onto `maintenance_work_order`.
- Presentation: `recent_closures` (five, newest first) on the work-order read, in the worklist, and on the per-asset list. The edge closure form disables submit until all three selects are chosen; the server gate remains authoritative.
